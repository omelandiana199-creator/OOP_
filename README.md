
# Лабораторна робота №3

**Тема:** Відпрацювання навичок роботи з класами, об'єктами та базовими механізмами ООП

**Мета:** Відпрацювати навички володіння класами, об'єктами та іншими механізмами ООП (інкапсуляція, успадкування, поліморфізм), які є у мові програмування Java. Створити консольний застосунок із застосуванням колекцій та файлового введення-виведення для збереження стану програми між запусками.

 **Варіант завдання:** (Варіант 4) Система обліку студентів та курсів.
 
Необхідно реалізувати систему керування навчальним процесом через консоль.

**Основні вимоги:**  Маніпуляції зі студентами, викладачами та курсами.  Список курсів із пагінацією.  Запис студентів на курси, виставлення оцінок та формування залікової книжки студента.  Наявність мінімум 2-3 факультетів.  Серіалізація для збереження інформації про студентів, курси та успішність у файл.  

**Теоретичні відомості та застосовані принципи ООП**

Під час розробки застосунку були використані такі принципи об'єктно-орієнтованого програмування:

**Інкапсуляція:** Усі поля даних у класах моделей (наприклад, Student, Course) приховані за допомогою модифікатора private або protected. Доступ до них здійснюється виключно через публічні методи (геттери) або спеціальні методи зміни стану (наприклад, setGrade()).

**Успадкування:** Створено абстрактний базовий клас Person (Людина), який містить спільні поля id та name. Від нього успадковуються класи Student (Студент) та Teacher (Викладач). 

**Поліморфізм:** У базовому класі Person оголошено абстрактний метод getRole(). Класи-спадкоємці реалізують цей метод по-різному, повертаючи відповідну роль (наприклад, "Студент" або "Викладач (Назва кафедри)").  

Архітектура програми Для забезпечення якості та розширюваності коду було застосовано професійний підхід на основі багатошарової архітектури (Layered Architecture), що дозволило розділити відповідальність (відповідно до принципу SRP - Single Responsibility Principle).Структура пакетів:model: Містить класи-сутності предметної області (Student, Teacher, Course, Faculty, Person).repository: Відповідає за збереження та завантаження даних. Використано сучасну бібліотеку Gson від Google та пакет java.nio для серіалізації даних у зручний текстовий формат JSON.  service: Містить бізнес-логіку програми (UniversityService). Виконує перевірки на існування об'єктів перед виставленням оцінок чи записом на курс. ui: Відповідає за взаємодію з користувачем через консоль (ConsoleUI). Перехоплює помилки та виводить зручне меню з пагінацією.  exception: Містить власні класи винятків (наприклад, EntityNotFoundException) для обробки непередбачених ситуацій.

**Інструкція з тестування (Користувацький сценарій)**

Для перевірки працездатності програми передбачено наступний сценарій:

Запустити програму. За відсутності бази даних система автоматично створить порожню.

Вибрати пункт 2 (Додати студента). Ввести унікальний ID, ім'я та обрати факультет (ФІТІС, ФЕУ, ФГТ).

Вибрати пункт 3 (Додати курс). Ввести ID курсу, назву дисципліни, ім'я викладача та кафедру.

Вибрати пункт 1 (Список курсів). Перевірити роботу пагінації (сторінкового виводу), яка відображає по 2 предмети на екран.  

Вибрати пункт 4 (Записати студента на курс). Ввести раніше створені ID студента та курсу.  

Вибрати пункт 5 (Виставити оцінку). Ввести ID студента, ID курсу та оцінку в балах. 

Вибрати пункт 6 (Залікова книжка). Ввести ID студента. 

Програма згенерує звіт про предмети та бали, які отримав студент.  

Вибрати пункт 0 (Вийти). Дані будуть збережені у файл university.json. При наступному запуску програми всі студенти та оцінки будуть відновлені.  Крім ручного тестування, бізнес-логіка програми (успадкування, поліморфізм, перевірка оцінок) покрита модульними тестами за допомогою фреймворку JUnit 5.

**Висновок** Під час виконання лабораторної роботи було створено повноцінну консольну систему для керування навчальним процесом. Було на практиці закріплено розуміння ключових парадигм ООП (успадкування, поліморфізму, інкапсуляції), роботу з колекціями (List, Map) для зберігання зв'язків між студентами та курсами. Застосування багатошарової архітектури, власних винятків та JSON-серіалізації дозволило зробити програму надійною, розширюваною та наближеною до стандартів комерційної розробки програмного забезпечення.  


# Лабораторна робота №4

**Тема**: Поліморфізм. Абстрактні класи. Enum. Records.

**Мета роботи** Отримати практичні навички використання поліморфізму, абстрактних класів, перетворення типів, перерахувань (enum), методів класу Object, копіювання об'єктів та records у мові програмування Java.  

**Завдання лабораторної роботи** Доопрацювати застосунок системи обліку університету з попередньої лабораторної роботи, реалізувавши такі вимоги:

1. Перетворити ієрархію класів на абстрактну з додаванням поліморфних методів.
2.  Додати перерахування (enum) із власними полями та методами.
3.   Перевизначити методи toString(), equals() та hashCode() для базових класів.
4.   Продемонструвати різницю між поверхневим (shallow) та глибоким (deep) копіюванням об'єкта.
5.   Використати records для створення простих класів передачі даних (DTO).
6.   Реалізувати сценарій обробки списку базового типу з визначенням конкретного типу через instanceof (pattern matching).
   
   **Теоретичні відомості та реалізація** 
   
  Абстрактні класи та поліморфізм. Базовий клас Person було перетворено на абстрактний. До нього додано абстрактний метод getDailyTask(). Класи-нащадки Student та Teacher реалізують цей метод по-різному (студент відвідує лекції, викладач — проводить заняття). Це дозволяє викликати метод getDailyTask() через посилання базового типу Person, демонструючи поліморфну поведінку. 
  
  Використання Enum із власною логікою. Створено перерахування CourseFormat, яке описує формат проведення курсу (ONLINE, OFFLINE, HYBRID). На відміну від простих констант, цей enum містить власні поля (опис та логічний прапорець потреби в аудиторії) і метод requiresClassroom(), що інкапсулює бізнес-логіку всередині перерахування. 
  
  Перевизначення методів класу Object. Для класів Person та Course перевизначено методи equals() та hashCode(). Порівняння об'єктів відбувається виключно за їхнім унікальним ідентифікатором (id для людини та courseId для курсу). Це правильний підхід для сутностей предметної області, оскільки дві людини з однаковим ID в системі вважаються однією особою, незалежно від поточних оцінок чи інших змінних полів. Також для зручного виводу даних перевизначено метод toString(). 
  
  Поверхневе (Shallow) та Глибоке (Deep) копіюванняУ класі Student реалізовано два підходи до копіювання:  Конструктор копіювання (Shallow Copy): Створює новий об'єкт студента, але мапа оцінок (grades) копіюється за посиланням. Зміни оцінок у копії впливають на оригінал.Метод deepCopy() (Deep Copy): Створює новий об'єкт студента та виділяє нову пам'ять для мапи оцінок (new HashMap<>(this.grades)). Об'єкти стають повністю незалежними один від одного.
Роботу обох методів наочно продемонстровано через окремий пункт консольного меню. 

Використання Records. Для передачі проміжних даних створено структури CourseStatRecord та PersonInfoRecord. Використання record дозволило автоматично згенерувати незмінні (immutable) об'єкти з геттерами, equals, hashCode та toString без написання шаблонного коду.  

  Pattern Matching (instanceof). У класі UniversityService створено метод генерації загального звіту generateUniversityReport(). Метод ітерується по єдиному списку типу List<Person>, обробляючи і студентів, і викладачів. За допомогою сучасної конструкції if (p instanceof Student s) відбувається одночасна перевірка типу та безпечне приведення (cast), що дозволяє витягти специфічні дані (наприклад, факультет для студента або кафедру для викладача) для формування звіту.  
  
  **Висновок:** Під час виконання лабораторної роботи було успішно впроваджено концепції ООП у застосунок для управління навчальним процесом. Реалізація абстрактних класів та поліморфізму дозволила зробити систему гнучкою, а застосування сучасних можливостей Java (таких як Records та Pattern Matching) значно скоротило обсяг коду та підвищило його читабельність. Також на практиці було досліджено різницю між поверхневим і глибоким копіюванням об'єктів пам'яті. 


 # Лабораторна робота №5
 
 **Тема:** Обробка винятків. Узагальнення (Generics). Тип Optional.

 **Мета роботи:** Отримати практичні навички створення та обробки власних виняткових ситуацій, використання узагальнених типів (Generics) з обмеженнями та застосування типу Optional для уникнення помилок відсутності значення.  
 
 **Завдання лабораторної роботи** 
 
 Доопрацювати консольний застосунок системи управління університетом:
 
 1. Створити власну ієрархію винятків (мінімум 3 класи: базовий, перевіряємий та неперевіряємий).
 2.  Забезпечити безпечну обробку винятків у коді за допомогою блоків try-catch.
 3.  Реалізувати узагальнений клас GenericRepository<T> з використанням обмежень параметрів типу (bounded type parameter).
 4. Замінити повернення null у методах пошуку на Optional із відповідною обробкою на стороні виклику.
 5.  Створити метод з використанням wildcard (? extends) для обробки колекцій різнотипних елементів наявної ієрархії.
 
  **Теоретичні відомості та реалізація**
  
  Створення власної ієрархії винятків. Для відображення доменних помилок предметної області розроблено таку ієрархію: UniversityException: Базовий перевіряємий (checked) виняток, успадкований від Exception.  CourseCapacityExceededException: перевіряємий виняток, що генерується, якщо студент намагається записатися більше ніж на 5 курсів одночасно. Містить додаткове поле з ID студента для деталізації помилки.  EntityNotFoundException: неперевіряємий (unchecked) виняток, успадкований від RuntimeException, який сигналізує про відсутність студента або курсу в базі даних при спробі пошуку.  
  Обробка виняткових ситуацій (try-catch). Вся взаємодія з користувачем ізольована в класі ConsoleUI. У головному циклі програми реалізовано глобальний блок try-catch, який перехоплює різні типи помилок:NumberFormatException — обробляє ситуації, коли користувач вводить текст замість числової оцінки.  CourseCapacityExceededException та EntityNotFoundException — виводять зрозуміле повідомлення про порушення бізнес-логіки замість аварійного завершення програми.  IllegalArgumentException — спрацьовує при спробі поставити оцінку за курс, на який студент не записаний.
Цей підхід запобігає "падінню" системи та забезпечує безперервну роботу програми.  

Узагальнення (Generics) та обмеження типів. Для уникнення дублювання коду створено узагальнений контейнер GenericRepository<T Identifiable<String extends>>. Інтерфейс Identifiable вимагає від усіх сутностей мати метод getId(). Це дозволило використовувати єдиний клас репозиторію як для збереження об'єктів Student, так і для Course, зберігаючи при цьому строгу типізацію. 

Використання типу Optional. Метод findById() в узагальненому репозиторії тепер повертає Optional<T>. На стороні сервісу це значення обробляється за допомогою конструкції orElseThrow(), яка автоматично генерує EntityNotFoundException, якщо об'єкт не знайдено, гарантуючи відсутність NullPointerException.  

Застосування Wildcards. У класі UniversityService реалізовано метод extractNames(List<? extends Person> people). Завдяки використанню wildcard (шаблону підстановки з верхньою межею), цей метод став універсальним: він може приймати колекцію студентів (List<Student>), колекцію викладачів (List<Teacher>) або змішану колекцію базового типу, і успішно витягувати з них імена.  

**Висновок:** Під час виконання лабораторної роботи програму було суттєво модернізовано з урахуванням стандартів надійності та безпеки Java. Створена ієрархія винятків дозволила чітко розмежувати системні помилки та помилки бізнес-логіки. Впровадження узагальнень (Generics) значно зменшило дублювання коду в шарі доступу до даних, а застосування Optional зробило контракт методів більш прозорим та захищеним від помилок відсутності значень. Програма стабільно обробляє некоректні вхідні дані та продовжує роботу без збоїв.


# Лабораторна робота №6

**Мета:** Отримати практичні навички роботи з класами String, StringBuilder/StringBuffer, регулярними виразами та форматованим введенням-виведенням.

1. Імпорт та розбір текстових даних (CSV-формат) в об'єкти застосунку з використанням мінімум 5 різних методів класу String.
2.  Формування табличного текстового звіту за допомогою класу StringBuilder (мінімум 20 операцій append/insert) з текстовим вирівнюванням колонок.

  **Теоретичні відомості та практична реалізація** 
  
  1. Обробка рядкових даних (Клас String)Для реалізації імпорту студентів із формату CSV створено метод importStudentFromCsvLine().
  2. Під час розбору рядка використано такі методи класу String:
trim() — для очищення вхідного рядка та його окремих частин від провідних та кінцевих пробілів.
replace() — для видалення можливих символів подвійних лапок ("), які часто зустрічаються при експорті CSV.
split(";") — для розділення суцільного рядка на масив підрядків (масив колонок) за символом-роздільником.
toLowerCase() — для нормалізації регістру при перевірці назви факультету (дозволяє системі розпізнавати "ФІТІС", "Фітіс" або "фітіс" однаково).
substring() — застосовано для безпечного отримання першої літери імені задля додаткової базової перевірки на порожнечу.3.2.
 3.Регулярні вирази (Regular Expressions)Перед збереженням даних студента в систему реалізовано сувору валідацію через регулярні вирази. Використано три патерни:   ID студента (^S-\\d{3,5}$): Вимагає, щоб ідентифікатор починався з літери S, дефіса та містив від 3 до 5 цифр.   Email-адреса (^[\\w.-]+@[\\w.-]+\\.[a-zA-Z]{2,}$): Перевіряє наявність локальної частини (алфавітно-цифрові символи, крапки, дефіси), символу @ та валідного домену, що закінчується мінімум на 2 літери (наприклад, .com або .ua). Перевірка здійснюється через компіляцію Pattern.compile().   Телефонний номер (^\\+380\\d{9}$): Жорстко фіксує український формат номера: обов'язковий код країни +380 на початку рядка, після якого мають йти рівно 9 цифр.

 4. Застосування самобалансованих структур (TreeMap)

 5.Побудова власного бінарного дерева пошуку (BST)

  Вставка (insert) реалізована рекурсивно: ключем впорядкування обрано ID студента. Якщо ID менший за поточний вузол, об'єкт поміщається в ліве піддерево, якщо більший — у праве.
  Обхід дерева реалізовано за алгоритмом In-Order (центрований обхід: ліве піддерево - корінь - праве піддерево). Даний алгоритм забезпечив виведення списку студентів у строго відсортованому за ID вигляді.
  
  6. Бенчмаркінг структур даних
  Для порівняння швидкодії ArrayList та LinkedList було проведено тестування продуктивності операції вставки в середину списку (index = size / 2) на обсязі 100 000 ітерацій.
 Результат: ArrayList виконав операції на порядок швидше, ніж LinkedList.
 Висновок: Попри те, що LinkedList виконує саму вставку вузла за O(1), процес пошуку потрібного індексу в середині списку вимагає O(N) операцій для кожного додавання (лінійний прохід). **Завдання лабораторної роботи**

1. Додати до існуючого коду навчальної системи породжувальні шаблони проєктування.
2. Реалізувати шаблони самостійно, без використання готових бібліотечних рішень чи сторонніх фреймворків.
3.  Доцільно обґрунтувати інтеграцію патернів у код, який розв'язував проблеми попередніх лабораторних робіт.
4.  Для претендування на високу оцінку реалізувати більше ніж один шаблон проєктування.


**Теоретичні відомості та практична реалізація** 

Для побудови професійної, масштабованої архітектури та виконання вимог на максимальну оцінку, у проєкт було інтегровано три породжувальні шаблони: Singleton (Одинак), Factory Method (Фабричний метод) та Builder (Будівельник). 

Патерн «Одинак» (Singleton) — Bill Pugh Implementation. У системі функціонує клас LoggerService, який відповідає за запис логів у текстові файли. У попередніх реалізаціях допускалося створення кількох екземплярів цього класу через оператор new. Це є архітектурним недоліком, оскільки паралельне звернення різних об'єктів логера до одного файлу може викликати виняток FileAlreadyInUseException та втрату даних. Система повинна гарантувати наявність лише одного екземпляра логера.

**Реалізація:**
Шаблон Одинак було реалізовано за найсучаснішим стандартом — Initialization-on-demand holder idiom (Bill Pugh Singleton).   Конструктор класу LoggerService було перекрито модифікатором private, що унеможливлює інстанціювання ззовні.Створено приватний статичний внутрішній клас InstanceHolder, який містить фінальне статичне поле з єдиним екземпляром логера.Реалізовано публічний метод getInstance(), який повертає цей об'єкт.
Перевага підходу: Підхід Bill Pugh є абсолютно потокобезпечним (Thread-Safe) на рівні JVM та забезпечує ліниву ініціалізацію (об'єкт створюється виключно в момент першого виклику getInstance()).

Патерн «Фабричний метод» (Factory Method) із Generics. Головний клас бізнес-логіки UniversityService був жорстко пов'язаний (tight coupling) із конкретними класами моделей, оскільки самостійно викликав їхні конструктори. При розширенні ієрархії (наприклад, додаванні нових типів персоналу) довелося б вносити зміни безпосередньо в сервіс.

**Реалізація:**
З метою інверсії управління та дотримання принципу Single Responsibility (Єдиної відповідальності) було розроблено сімейство фабрик. Створено абстрактний інтерфейс PersonFactory<T D Person, extends>. Застосування параметризованих типів (Generics) дозволило створити гнучкий контракт для генерації будь-яких дочірніх класів Person.Розроблено дві конкретні фабрики: StudentFactory (реалізує PersonFactory<Student, Faculty>) та TeacherFactory (реалізує PersonFactory<Teacher, String>).  
Перевага підходу: Завдяки Generics метод create() відразу повертає об'єкт потрібного типу (Student або Teacher). Це дозволило повністю уникнути небезпечного низхідного приведення типів, яке часто стає причиною помилок часу виконання. Тепер UniversityService нічого не знає про процес конструювання об'єктів — він лише отримує готові екземпляри від фабрики.

Патерн «Будівельник» (Builder) із захистом Fail-Fast. Клас Course має багатокомпонентний конструктор. Передача параметрів (наприклад, ідентифікатора, назви, викладача, формату) безпосередньо в конструктор є вразливою: розробник може випадково переплутати місцями аргументи однакового типу (String), що призведе до логічних помилок без спрацьовування компілятора.

**Реалізація:**
Усередині класу Course було спроєктовано статичний вкладений клас Builder. Він реалізує текучий інтерфейс (Fluent Interface), де кожен метод ініціалізації (setTitle, setTeacher) повертає посилання на сам Builder (return this;).Ключовою архітектурною особливістю стала інтеграція принципу Fail-Fast (швидке падіння) у фінальному методі build(). За допомогою методів Objects.requireNonNull() будівельник жорстко валідує всі поля перед викликом приватного конструктора Course.
Перевага підходу: Якщо під час конструювання об'єкта буде пропущено критично важливе поле (наприклад, викладач або формат), система миттєво згенерує NullPointerException ще до моменту додавання курсу в базу даних, тим самим захищаючи цілісність даних застосунку.

 **Висновок:** Під час виконання лабораторної роботи №9 було освоєно застосування породжувальних шаблонів проєктування (GoF).
Написання шаблонів здійснено самостійно, з урахуванням сучасних стандартів розробки мовою Java: застосовано типобезпечні абстрактні фабрики на базі узагальнень (Generics), реалізовано високопродуктивний потокобезпечний Одинак (метод Bill Pugh) та розроблено Будівельник із проактивною валідацією стану об'єкта (Fail-Fast). Доведено, що впровадження шаблонів суттєво зменшує зв'язність коду (Loose Coupling) та підвищує надійність системи, відокремлюючи складний процес конструювання об'єктів від основної бізнес-логіки.
