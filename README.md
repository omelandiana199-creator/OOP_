# Лабораторна робота №2

**Тема:** Класи. Типи зв'язків.

**Мета роботи:** Отримати практичні навички для розробки програм з використання принципів зв'язаності об'єктів.

**Завдання:**
За допомогою створення нових класів та інтерфейсів розширити модель із першої лабораторної роботи, додавши та програмно реалізувавши типи зв'язків між об'єктами (Композиція, Агрегація, Асоціація, Наслідування). Модель має містити не менше шести класів та зберігати ієрархію з глибиною мінімум три рівні. Кожен клас має бути розміщений в окремому файлі.

**Опис виконання роботи:**
Відповідно до поставленого завдання, було розширено раніше розроблену об'єктно-орієнтовану модель прийому замовлень у харчувальні. З метою виконання вимог щодо наявності різних типів зв'язків між об'єктами, до загальної архітектури було інтегровано нові сутності та налаштовано їхню взаємодію:

1. **Асоціація (Association):** Було реалізовано зв'язок між класом `Order` (Замовлення) та новоствореним класом `Customer` (Клієнт). Замовлення асоціюється з конкретним клієнтом, проте об'єкти обох класів існують абсолютно незалежно один від одного, що підтверджує слабкий тип зв'язку.
2. **Агрегація (Aggregation):** Продемонстровано взаємодію між класом `Order` та переліком об'єктів базового типу `MenuItem` (Страви). Клас замовлення агрегує в собі масив страв, але не є їхнім одноосібним власником, оскільки об'єкти страв можуть існувати в системі (наприклад, у загальному меню) незалежно від статусу конкретного замовлення.
3. **Композиція (Composition):** Спроєктовано жорсткий зв'язок між класом `Order` та класом `Receipt` (Чек). Життєвий цикл об'єкта `Receipt` повністю контролюється класом `Order`. Чек генерується виключно всередині замовлення при його обробці, що унеможливлює існування фіскального документа без відповідного замовлення. Для цього конструктор класу `Receipt` було приховано (обмежено на рівні пакета).
4. **Успадкування (Inheritance):** Збережено та інтегровано багаторівневу ієрархію (наприклад, `MenuItem` ➔ `FoodItem` ➔ `Pizza`), що задовольняє вимогу щодо наявності ієрархії з глибиною мінімум три рівні.



Усі класи винесено в окремі файли згідно з принципом єдиної відповідальності. Коректність логіки взаємодії між створеними об'єктами (передача клієнта в замовлення, додавання позицій, внутрішня генерація чека) була перевірена та підтверджена за допомогою написання автоматизованих модульних тестів (JUnit).

**Висновок:**
У результаті виконання лабораторної роботи було успішно закріплено теоретичні знання та отримано практичні навички використання принципів зв'язаності об'єктів в об'єктно-орієнтованому програмуванні. Шляхом розширення існуючої моделі прийому замовлень було наочно продемонстровано різницю між асоціацією, агрегацією та композицією.

Практична реалізація довела, що правильний вибір типу зв'язку між класами (від слабкої асоціації до жорсткої композиції) є критично важливим етапом проєктування. Це дозволяє чітко розмежувати життєві цикли об'єктів, уникнути витоків пам'яті та забезпечити гнучкість, модульність і надійність програмної архітектури при подальшому масштабуванні системи.
