# Лабораторна робота №1
**Тема:** Класи. Основні їх елементи. Інтерфейси. Суть та особливості

**Мета роботи:** Отримати практичні навички для розробки програм з використання класів та інтерфейсів у мові Java.

**Завдання:**
Згідно з варіантом №4, необхідно розробити модель прийому замовлень у харчувальні. Розроблена модель повинна містити не менше шести класів із глибиною ієрархії мінімум три рівні. Кожен клас має бути розміщений в окремому файлі. До основної моделі вимагається додати та імплементувати два інтерфейси. У рамках математичної складової роботи, також реалізувати 10 запропонованих математичних задач.

**Опис виконання роботи:**
Відповідно до поставленого завдання, було спроєктовано та програмно реалізовано об'єктно-орієнтовану модель прийому замовлень у харчувальні. Архітектуру моделі побудовано на базі ієрархії з шести класів, глибина успадкування якої становить три рівні. З метою дотримання стандартів організації коду, кожен створений клас було винесено в окремий файл. Додатково архітектуру було розширено: створено та імплементовано два інтерфейси, що доповнюють функціонал основних об'єктів.

Окремим розширеним етапом стала алгоритмічна реалізація повного комплексу з 10 математичних задач. Для їх вирішення було розроблено єдиний утилітний клас із активним застосуванням сучасних інструментів Java Stream API. Серед успішно реалізованих завдань: знаходження суми масиву, обчислення середнього арифметичного, пошук мінімуму та максимуму, перевірка та фільтрація простих чисел, обчислення факторіалу (ітеративно та рекурсивно), реверс масиву, генерація чисел Фібоначчі, видалення дублікатів, сортування бульбашкою з підрахунком обмінів, а також підрахунок парних і непарних чисел. Правильність роботи як бізнес-логіки моделі харчувальні, так і всіх математичних методів була підтверджена за допомогою модульного тестування (фреймворк JUnit 5).

**Висновок:**
У результаті виконання лабораторної роботи було успішно застосовано та закріплено практичні навички розробки програм із використанням класів та інтерфейсів у мові Java. Завдяки проєктуванню моделі прийому замовлень у харчувальні було детально досліджено механізми успадкування та особливості побудови багаторівневих ієрархій класів. Винесення кожного класу в окремий файл на практиці довело необхідність чіткої структуризації програмного коду, а процес імплементації інтерфейсів наочно продемонстрував гнучкі підходи до розширення функціональності об'єктів.

Водночас було значно поглиблено навички розробки алгоритмів шляхом програмної реалізації 10 математичних задач. Застосування функціонального підходу (Stream API) дозволило суттєво оптимізувати код, а написання модульних тестів закріпило розуміння важливості автоматизованої перевірки для забезпечення якості програмного забезпечення. Отримані знання є міцною базою для подальшого проєктування надійних об'єктно-орієнтованих систем.

# Лабораторна робота №2

**Тема:** Класи. Типи зв'язків.  

**Мета роботи:** Отримати практичні навички для розробки програм з використання принципів зв'язаності об'єктів.  

**Завдання:** За допомогою створення нових класів та інтерфейсів розширити модель із першої лабораторної роботи, додавши та програмно реалізувавши типи зв'язків між об'єктами (Композиція, Агрегація, Асоціація, Наслідування). Модель має містити не менше шести класів та зберігати ієрархію з глибиною мінімум три рівні. Кожен клас має бути розміщений в окремому файлі.

**Опис виконання лабораторної роботи:**
Відповідно до поставленого завдання, було розширено раніше розроблену об'єктно-орієнтовану модель прийому замовлень у харчувальні. 
З метою виконання вимог щодо наявності різних типів зв'язків між об'єктами, до загальної архітектури було інтегровано нові сутності та налаштовано їхню взаємодію:  Асоціація (Association): Було реалізовано зв'язок між класом Order (Замовлення) та новоствореним класом Customer (Клієнт). Замовлення асоціюється з конкретним клієнтом, проте об'єкти обох класів існують абсолютно незалежно один від одного, що підтверджує слабкий тип зв'язку.Агрегація (Aggregation): Продемонстровано взаємодію між класом Order та переліком об'єктів базового типу MenuItem (Страви). Клас замовлення агрегує в собі масив страв, але не є їхнім одноосібним власником, оскільки об'єкти страв можуть існувати в системі (наприклад, у загальному меню) незалежно від статусу конкретного замовлення.Композиція (Composition): Спроєктовано жорсткий зв'язок між класом Order та класом Receipt (Чек). Життєвий цикл об'єкта Receipt повністю контролюється класом Order. Чек генерується виключно всередині замовлення при його обробці, що унеможливлює існування фіскального документа без відповідного замовлення. Для цього конструктор класу Receipt було приховано (обмежено на рівні пакета).Успадкування (Inheritance): Збережено та інтегровано багаторівневу ієрархію (наприклад, MenuItem ➔ FoodItem ➔ Pizza), що задовольняє вимогу щодо наявності ієрархії з глибиною мінімум три рівні.  Усі класи винесено в окремі файли згідно з принципом єдиної відповідальності. Коректність логіки взаємодії між створеними об'єктами (передача клієнта в замовлення, додавання позицій, внутрішня генерація чека) була перевірена та підтверджена за допомогою написання автоматизованих модульних тестів (JUnit). 

**Висновок:**
У результаті виконання лабораторної роботи було успішно закріплено теоретичні знання та отримано практичні навички використання принципів зв'язаності об'єктів в об'єктно-орієнтованому програмуванні. Шляхом розширення існуючої моделі прийому замовлень було наочно продемонстровано різницю між асоціацією, агрегацією та композицією.  Практична реалізація довела, що правильний вибір типу зв'язку між класами (від слабкої асоціації до жорсткої композиції) є критично важливим етапом проєктування. Це дозволяє чітко розмежувати життєві цикли об'єктів, уникнути витоків пам'яті та забезпечити гнучкість, модульність і надійність програмної архітектури при подальшому масштабуванні системи.
